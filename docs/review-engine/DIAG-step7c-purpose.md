# DIAG — Step 7c(예시도/개념도) 목적·기능 정립 진단

> 브랜치: `review-engine/diag-step7c-purpose` · READ-ONLY 진단(코드 0)
> 결론 한 줄: **예시도의 목적은 정당하다** — 장치 블록도(step_07)가 못 보여주는 **비(非)블록 측면**(실제 UI 화면·사용 시나리오·데이터 테이블·기기 외관·동작 장면)을 시각화해 **이해 보조 + 도면 뒷받침**을 한다. **그러나 생성 프롬프트가 그 목적을 명문화하지 않고 "시각 스타일(블록도 금지)"에만 90% 치우쳐**, ① 어떤 청구항 구성을 시각화하는지 **결속이 약하고**, ② 도면 내 요소의 **의미(부호↔이름)를 캡처하지 않아** 부호의 설명·상세설명이 부정확하며, ③ 참조번호 범위가 **불일치(31~79 vs 31~99)** 해 일부 유형(프로세스 81~99)의 부호가 통째 누락된다. → **품질 개선(비전 루프 등) 이전에 "목적 정립"이 선행돼야 한다**(사용자 직관이 정확).

## 1. 예시도 생성 "목적" — 프롬프트·코드가 말하는 것

### 1-1. 프롬프트가 명시하는 것 (5523~5600) — ★ 스타일 위주, 목적 빈약
생성 프롬프트(`runConceptDiagramStep` 5523)의 거의 전부는 **"무엇을 그리지 마라 / 어떻게 그려라"**:
- ⛔ 블록도·플로우차트 금지, "~부" 박스 금지, 색상 금지, 영문 접미 부호 금지, step_07 블록도와 차별화(5525~5530, 5596~5600 자체검증).
- ✅ 시각 어휘(스틱피겨·화면·말풍선·디바이스·테이블)와 SVG 기술규칙(5539~5556).
- 유형별 지시도 **형태**만("스마트폰 외곽+UI", "스틱피겨+말풍선", "격자 테이블" 5560~5575).

→ ★ **목적(왜·법적 기능)을 말하는 문장이 사실상 없다.** "이 예시도는 청구항의 어느 구성을 무슨 목적(뒷받침/이해보조)으로 시각화하라"가 **부재**. 청구범위는 `outputs.step_06` 를 **"참고만 — 블록 복제 금지"(5584)** 로 느슨히 줄 뿐, 특정 구성에 **결속하지 않는다**.

### 1-2. 코드가 드러내는 "의도된" 목적 — 자동 추천 매핑(5479~)
`autoDetectConceptDiagrams()` (5479) 가 **청구항 키워드 → 유형**으로 추천하며, 여기에 의도된 목적이 암묵 인코딩돼 있다:
| 유형 | 트리거 키워드(청구항) | 의도 |
|------|----------------------|------|
| ui_screen | 디스플레이·표시부·화면·인터페이스·터치스크린·GUI (5484) | UI 발명 → 실제 화면 예시 |
| user_scenario | 사용자·단말·클라이언트·요청·응답·전송·수신 (5487) | 상호작용 발명 → 사용 흐름 한 장면 |
| data_structure | DB·테이블·스키마·레코드·필드·저장부·메모리 (5490) | 자료구조 발명 → 데이터 테이블 예시 |
| device_appearance | (자동 추천 없음 — 수동) | 기기 물리 외형 |
| process_scene | (자동 추천 없음 — 수동) | 처리 과정 물리 메타포 |

→ ★ 목적·유형 매핑은 **추천 로직에만** 있고 **생성 프롬프트엔 흘러들어가지 않는다**(추천은 "어떤 유형을 켤지"만 정할 뿐, 생성 시 "그 유형이 어느 구성을 왜 그리는지"는 프롬프트에 안 들어감).

## 3. 명세서 통합 — 예시도의 실제 역할 (vs 장치 도면)

```
청구항(step_06) ──MUST──▶ 예시도(step_07c) 추천(autoDetect 5479)       [언제 만드나]
예시도(step_07c) ──MUST──▶ 상세설명(step_08)·부호의 설명(step_18) (2238) [무엇에 반영되나]

(A) 도면의 간단한 설명: "도 N은 …의 [유형]을 나타내는 예시도이다." 1줄 등재
    (extractBriefDescriptions 3046~3053)
(B) 상세설명(step_08): 프롬프트에 "도 N: [유형] (참조번호: …)" 주입(4222) →
    LLM이 "도 N을 참조하면, …" 형태로 기술. ★ 단, 주입은 유형라벨+번호뿐(요소 의미 없음).
(C) 부호의 설명(step_18): 예시도 참조번호(31~99) 등재(장치 100~999와 구분).
(D) 다운로드: SVG→PNG→PPTX 별도(downloadConceptPptx). 본문 .doc엔 이미지 미포함(별지).
```

**vs 장치 도면(step_07)**: step_07은 **발명의 구조(구성요소-관계)를 블록도**로(청구항 구성요소 100~999, E-11 정합 검사 대상). step_07c는 **그 구조가 실제로 어떻게 보이/쓰이는지를 시각 장면**으로(31~99, E-11 밖). 즉 step_07=구조 증명, step_07c=실시·이해 보조. **상보적**이며 역할 구분은 명확하다.

## 4. 목적 대비 현재 구현 부합도 ★ (핵심)

**판정: 목적은 타당하나, 생성이 그 목적에 "결속"되지 않아 부합도 부분적(↓). 모호함의 핵심은 프롬프트의 목적 부재.**

| # | 격차 | 근거(file:line) | 결과 |
|---|------|-----------------|------|
| G1 | ★ **목적 미명시(스타일 과편향)** — 프롬프트가 "블록도 금지/시각형태"만 말하고, "어느 청구항 구성을 무슨 목적으로 시각화"를 안 말함 | 5523~5600(전부 형태·금지) | 예쁘지만 **발명 핵심과 무관**한 그림 위험 |

| G4 | ★ **참조번호 범위 불일치** — 추출 필터 `31~79`(2741·5636) vs 유형정의 `~99`(84) vs step_08 주입 `31~99`(4222) vs 프롬프트 `31~79`(5554) | 다중 | **프로세스 장면(81~99) 부호 전량 추출 누락** → 부호의 설명에 안 들어감 |

## 5. 개선 방향 — 목적 정립 우선(품질 개선 전)

| 우선 | 방향 | 내용 |
|------|------|------|
| ★ P1 | **목적의 명문화 + 청구항 결속** | 생성 프롬프트에 "이 예시도는 청구항 [N]의 [구성 X]를 [이해보조/실시예 뒷받침] 목적으로 시각화한다"를 유형별로 주입(추천 5479의 매핑을 생성으로 전달 — G1·G2·G5 해소) |
| ★ P2 | **요소 의미 캡처** | SVG 생성 시 `요소 라벨↔참조번호` 매핑을 함께 산출·저장(예: `refMap:{31:'검색창',...}`) → 상세설명·부호의 설명이 정밀(G3 해소). T2(비전 분석)의 elements 추출 포맷 재사용 가능 |
| ★ P3 | **참조번호 범위 통일** | 31~99 단일 기준으로 추출 필터·프롬프트·step_08 주입·유형정의 일치(G4 — 프로세스 장면 누락 버그 해소) |
| P4 | 프롬프트 단일화 | 메인·캐스케이드 단일 소스(G6, math 단일화 패턴) |
| P5 | (품질) 비전 정련 루프 | ★ **P1~P3 이후** 적용 — 목적 결속된 도면을 비전으로 정련(이전 진단 C2). 목적 먼저, 품질 나중 |

> 순서 원칙: **P1(목적 명문화)·P2(의미 캡처)·P3(번호 통일) → P4 단일화 → P5 품질(비전).** 목적·결속을 세우기 전에 품질 루프부터 돌리면 "정확히 엉뚱한" 도면이 더 정교해질 뿐이다.

## 6. 핵심 질문 — 직답

- **예시도를 왜 생성하나(명세서 역할)** → 장치 블록도(step_07)가 못 보여주는 **비블록 측면**(UI·시나리오·데이터·외관·동작)을 시각화해 **이해 보조 + 도면 뒷받침**. 간단한설명 1줄(3046) + 상세설명 "도 N 참조"(4222) + 부호의 설명(31~99)으로 통합.
- **5유형 각각 무슨 기능·언제** → UI화면(디스플레이/GUI 청구), 시나리오(상호작용/요청·응답), 데이터구조(DB/테이블/필드), 장치외관(물리 기기), 프로세스(처리 과정). 앞 3종은 청구항 키워드로 **자동 추천**(5484~5490), 뒤 2종은 수동.
- **청구항·상세설명과 연결** → 청구항이 예시도를 추천(step_06 MUST step_07c), 예시도가 상세설명·부호를 무효화·반영(step_07c MUST step_08·step_18). 단 **상세설명 주입은 유형라벨+번호뿐**(요소 의미 없음 — G3).
- **장치 도면(step_07)과 차이** → step_07=**구조 증명**(블록도, 100~999, E-11 검사), step_07c=**실시·이해 보조**(시각 장면, 31~99, E-11 밖). 상보적.
- **★ 현재 구현이 목적에 부합하나** → **부분적.** 목적은 타당하나 **생성 프롬프트에 목적이 명시·결속되지 않아**(G1·G2·G5) 산출물이 목적과 어긋날 수 있고, **요소 의미 미캡처(G3)·번호 범위 불일치(G4, 프로세스 부호 누락)** 로 명세서 뒷받침이 약하다. → **목적 정립(P1~P3)이 품질 개선보다 선행**.
