# DIAG — 오염검출 false-positive: 정형 서두·조문이 forbiddenSpan 으로 잡힘

> 브랜치: `review-engine/diag-contam-false-positive` · 코드 변경 0 (진단 문서만)
> 증상(콘솔 확정): `Template contamination: 1 items, high` / forbiddenSpan `"특허법 제42조제3항제1호..."` / match `"귀청께서는 2026.04.10.자로 ... 의견제출통지서를..."`
> 결론 한 줄: **`제N항` 마커가 "청구항 제N항(사건고유)"과 "특허법 제N조 제M항(정형 조문)"을 구분하지 못하고, 보일러플레이트 화이트리스트가 exact-string(띄어쓰기·번호 고정)이라 실제 조문/서두 변형을 못 걸러 → 정형 문장이 forbiddenSpan 에 들어가고 → 새 의견서의 동일 정형 서두가 high 오염으로 차단된다.**

---

## 0. 재현(실측) — 정형 문장이 forbiddenSpan 으로 통과

현재 추출 규칙(HIGH_RE + 화이트리스트)을 실제 문장에 적용:

| # | 문장 | HIGH_RE | whitelist | forbiddenSpan? |
|---|------|---------|-----------|----------------|
| 0 | `특허법 제42조제3항제1호 및 동조제4항제2호에 대하여…` (정형 조문) | ✅(제3항/제4항) | ❌ | **push (오검출)** |
| 1 | `귀청께서는 2026.04.10.자로 …특허법 제42조 제3항…의견제출통지서…` (정형 서두) | ✅(제3항) | ❌ | **push (오검출)** |
| 2 | `청구항 제3항의 가중 보정부는 인용문헌 2의 필터와 상이…` (진짜 사건고유) | ✅ | ❌ | push (정상) |

→ [0]·[1] 정형 문구가 [2] 진짜 고유문구와 **동일하게** forbiddenSpan 에 적재됨. 화이트리스트는 셋 다 ❌(못 거름).

## 1. forbiddenSpan 이 정형 문구를 잡는 지점 (file:line)

### (a) 추출 — `Opinion.sanitizeTemplate` (opinion.js:1259–1268)
```js
var HIGH_RE = [ /제\s*\d+\s*항/, /청구항\s*\d+/, /인용문헌\s*\d+|.../, /【\d{4}】/, /\d{4}-\d{6,}/ ];  // 1252
rawText.split(/[.\n]/).forEach(function(s) {
  var t = s.trim();
  if (t.length < 25 || t.length > 200) return;                                  // 1262
  if (!HIGH_RE.some(re => re.test(t))) return;                                   // 1264 ← 제N항이면 통과
  if (KOREAN_PATENT_BOILERPLATE.some(bp => t.indexOf(bp) >= 0)) return;          // 1266 ← exact-string, 변형 못거름
  forbiddenSpans.push(t.slice(0, 80));                                           // 1267 ← 정형 문장 적재
});
```
- **HIGH_RE `/제\s*\d+\s*항/` (1253)** 가 조문의 "제3항/제4항"에 적중 → 1264 통과.
- **화이트리스트(1266)** `KOREAN_PATENT_BOILERPLATE`(1174–1196)는 `'특허법 제42조 제4항'`처럼 **띄어쓰기·번호가 고정된 exact substring**. 실제 통지서는 `"제42조제3항제1호"`(무공백·제3항·제N호)라 `indexOf` 불일치 → 못 거름.
- 표준 서두 `'의견제출통지서를 수령하였기에'`도 고정 문구. 실제 서두는 `"의견제출통지서를 발송하였습니다"`(심사관 주체)·`"송부받았는바"` 등 변형이라 불일치.

### (b) 검증 — `Opinion.validateNoTemplateContamination` (opinion.js:1294–1322)
```js
var isBoilerplate = KOREAN_PATENT_BOILERPLATE.some(bp => trimmed.indexOf(bp) >= 0);  // 1299 동일 exact-string
var isHighRisk    = HIGH_RE.some(re => re.test(trimmed));                            // 1301 동일 제N항
for (len=20..50) if (opinionText.indexOf(chunk)>=0) {                                // 1303 새 의견서에 그 청크 존재?
  sev = isBoilerplate ? 'low' : isHighRisk ? 'high' : 'medium';                      // 1307 ← 조문=high
}
```
- forbiddenSpan 에 들어간 정형 서두/조문의 앞 20–50자 청크를 **새 의견서**에서 찾는다. 새 의견서도 **같은 정형 서두("귀청께서는…의견제출통지서")·같은 조문("특허법 제42조 제N항")** 을 쓰므로 청크 일치.
- `isHighRisk`(제N항 적중)=true, `isBoilerplate`(exact-string)=false → **severity `high`** (1309) → `clean:false` → startOpinionDraft 3474 에서 차단(throw kind=contamination).

## 2. 근본 원인 — `제N항` 마커 과적재 + exact-string 화이트리스트

### (1) `제\s*\d+\s*항` 이 두 가지를 구분 못 함 (overloaded)
- **청구항 제N항** = 사건고유(이 출원의 청구항 번호) → forbiddenSpan 대상이 맞음.
- **특허법 제N조 제M항** = 정형 조문(모든 의견서 공통, 사건무관) → forbiddenSpan 이면 안 됨.
- 정규식 `/제\d+항/` 은 둘 다 적중. "제3항"이 *청구항 3항*인지 *조문 3항*인지 문맥을 안 봄.

### (2) 화이트리스트가 exact substring (취약)
- `'특허법 제42조 제4항'` 처럼 **조 번호·항 번호·띄어쓰기가 고정**. 실제 통지서 표기는 다양: 무공백(`제42조제3항`), 다른 항/호(`제3항제1호`, `동조제4항제2호`), 다른 조(`제29조`/`제45조`).
- 서두도 주체·어미 변형(`발송하였습니다`/`송부받았는바`/`통지하신 바`)이라 `'…수령하였기에'` 고정문과 불일치.
- → 화이트리스트가 "우연히 적중한 보일러플레이트를 빼주는 2차 보호"(주석 1172) 역할을 **실패**.

### (3) 추출·검증 양쪽이 같은 취약 기준을 공유
- 추출(1264/1266)·검증(1299/1301)이 **동일한** HIGH_RE·exact-whitelist 사용 → 한쪽만 고쳐선 안 되고 **양쪽 동시** 정밀화 필요.

## 3. 정형 vs 사건고유 구분법 (조문·서두 제외 신호)

| 구분 | 예 | 신호(문맥) | forbiddenSpan? |
|------|-----|-----------|----------------|
| **정형(제외)** 법조 인용 | `특허법 제42조 제3항 제1호`, `동조 제4항` | 인접 `특허법\|법\|제\d+조\|동조\|제\d+호` | ❌ 제외 |
| **정형(제외)** 표준 서두/결어 | `귀청께서는 …의견제출통지서…`, `이상과 같이…` | `의견제출통지서\|귀청\|일자(\d{4}\.\d+\.\d+)` | ❌ 제외 |
| **고유(유지)** 청구항 번호 | `청구항 제3항`, `본원 청구항 제1항` | 인접 `청구항\|본원` | ✅ 유지 |
| **고유(유지)** 인용·단락·출원 | `인용문헌 2`, `【0072】`, `2024-0012345` | 그 자체 | ✅ 유지 |
| **고유(유지)** 기술내용 | `가중 보정부`, `120℃`, `TF-IDF` | 구성·수치·영문(이미 _maskCaseSpecific 대상) | ✅ 유지 |

★ 핵심 신호: **`제N항`이 법조 문맥(특허법/제N조/동조/제N호 인접)이면 조문(정형) → 제외**, **청구항 문맥(청구항/본원 인접)이면 고유 → 유지**.

## 4. 해결안 (수정은 별도 PR — 추출·검증 동시 적용 필수)

### (A) 마커 정밀화 — 근본 (권장)
`제N항` 단독 마커를 **법조 문맥에서 veto**한다. 즉 문장에 법조 신호가 있으면 그 `제N항`은 조문으로 보고 사건고유 마커에서 제외.
- 추출(1252 HIGH_RE)·검증(1284 HIGH_RE)에서 `/제\s*\d+\s*항/` 의 분류 전에 **법조 가드** 추가:
  ```js
  var STATUTE_RE = /(특허법|실용신안법|디자인보호법|상표법|법)\s*제\s*\d+\s*조|동\s*조|제\s*\d+\s*호/;
  // 문장이 STATUTE_RE 적중이고, 청구항 문맥(청구항|본원\s*청구항)이 없으면 → 그 제N항은 조문(정형) → 마커 제외
  ```
- 청구항 마커는 `/청구항\s*제?\s*\d+\s*항?/` 처럼 **청구항 문맥을 요구**하도록 좁힌다(맨 `제N항`은 법조 문맥이 아닐 때만 고유).
- → [0][1] 정형 문장은 법조/서두 신호로 제외, [2] `청구항 제3항`+`인용문헌 2`+`가중 보정부`는 여전히 잡힘.

### (B) 화이트리스트 일반화 — 보강
`KOREAN_PATENT_BOILERPLATE` 의 exact-string 의존을 **정규식 보일러플레이트**로 보강(추출 1266·검증 1299 동일):
```js
var BOILERPLATE_RE = [
  /(특허법|법)\s*제\s*\d+\s*조(\s*제\s*\d+\s*항)?(\s*제\s*\d+\s*호)?/,  // 법조 인용(번호 무관)
  /동\s*조\s*제\s*\d+\s*항/,                                          // "동조 제N항"
  /의견제출통지서/, /귀\s*청/,                                        // 표준 서두
  /\d{4}\.\s*\d{1,2}\.\s*\d{1,2}/,                                   // 통지/기준 일자
];
```
- exact-substring(`indexOf`) 대신 패턴 적중이면 보일러플레이트로 분류 → 추출 단계 제외 + 검증 단계 `low` 강등.

### 적용 위치(양쪽 필수)
- 추출: `sanitizeTemplate` 1264–1266 — 법조/서두면 `forbiddenSpans.push` 안 함.
- 검증: `validateNoTemplateContamination` 1299–1301 — `isBoilerplate` 를 정규식으로, 법조 문맥의 `제N항`은 `isHighRisk` 에서 제외(`low`).
- ★ 두 곳 기준 불일치 시 한쪽이 다시 잡으므로 **동일 헬퍼**(예: `_isBoilerplateSentence(t)` / `_caseSpecificMarkers(t)`)로 공유 권장.

## 5. 보존해야 할 것 (과잉수정 경계)
- **진짜 누수는 계속 잡아야 한다**: 다른 사건의 **인용문헌 번호**(인용문헌 2)·**단락번호**(【0072】)·**출원번호**(2024-…)·**기술 구성/수치/용어**(가중 보정부·120℃·TF-IDF). 이들은 법조/서두 신호가 없으므로 (A)(B) 적용 후에도 forbiddenSpan/high 유지.
- **청구항 번호**는 약한 마커(모든 사건이 제1~N항 보유)지만, 청크가 기술명사까지 포함(`청구항 제3항의 가중 보정부…`)하면 타 사건과 불일치라 false-positive 위험 낮음 — 청구항 문맥은 유지하되 단독 "제N항"만으론 high 안 되게 하는 것도 고려 가능(선택).

## 6. 사용자 확인용 (다음 수정 전)
- 멈춤 시 콘솔 `[Opinion.contam HIGH #N] forbiddenSpan:` 에 찍힌 문장이 **법조/서두 정형**인지(예상: 그렇다).
- 같은 로그의 `match context` 가 새 의견서의 **동일 정형 서두/조문**인지(예상: 그렇다).

**요지: `제N항`이 조문·청구항을 구분 못 하고 화이트리스트가 exact-string이라 정형 서두·조문이 forbiddenSpan→high 로 오검출. 수정 방향은 (A) 법조/서두 문맥 veto + (B) 화이트리스트 정규식화를 추출·검증 양쪽에 동일 적용. 진짜 기술내용·인용·단락·출원번호 누수는 그대로 잡는다.**
