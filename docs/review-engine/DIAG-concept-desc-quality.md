# DIAG — ① 명세서 본문 "청구항 N" 부적절 언급 + ② 예시도 설명이 외형만(장치 구성에 의한 동작·구현 누락)

> 브랜치: `review-engine/diag-concept-desc-quality` · 기준: `origin/main`(4b506b2, #213 포함) · 코드 변경 0
> 증상: ① 검토 반영 후 "청구항 3 및 청구항 5에 관련하여" 등 청구항 번호 직접 언급(명세서 부적절). ② 예시도 설명이 도면 외형만 — 그 구성이 장치 도면 구성에 의해 어떻게 동작·구현(SW→HW)되는지 누락.

## 0. 결론 (한 줄)

**① 출처는 주로 step_08 "생성"이다.** 생성·반영 어느 프롬프트에도 **"상세설명 본문에 청구항 번호(청구항 N/제N항)를 직접 언급하지 마라"는 규칙이 없다.** 생성 프롬프트는 오히려 "청구항"을 다수 참조(4385·4412·4489)해 LLM이 "청구항 3에 관하여"를 쓸 수 있고, 후처리에도 이를 제거하는 sanitizer가 없다. applyReview는 가드(5268 `청구항\s*\d+`)로 "청구항 N" 편집을 드롭하나 **"제N항" 형태는 가드 누락** + 검토 결과(step_13)가 "청구항 N"으로 가득해 유도 압력이 있다.

**② 예시도 설명 지시(4492)는 "예시도의 구성·동작·부호(31~99)"만 요구**하고, **"예시도의 화면/시나리오가 장치 도면 구성(100~)에 의해 어떻게 동작·구현되는지(소프트웨어→하드웨어)"를 기술하라는 지시가 없다.** [예시도 설계] 데이터(step_07c)도 refMap+briefDesc(외형)만이라 장치-구성 연결 정보가 없다 → 외형만 기술되고 실질적 시나리오가 안 된다.

## 1. ★ 문제 ① — "청구항 N" 표현 어디서 (생성? 반영?)

### 1-1. 본문 청구항-번호 언급 금지 규칙 = **전무**
- step_08 생성 프롬프트: "청구항 원문을 그대로 출력하지 마라"(4443)는 **청구항 텍스트 출력 금지**일 뿐, **번호 언급 금지가 아니다.**
- applyReview edit-gen 프롬프트: "⛔ 【청구항 N】, 청구항 1 등 청구항 헤더/번호/구조 절대 금지"(5460-격) — **CONTENT의 청구항 헤더 금지**.
- ⛔ 어디에도 **"상세설명 본문에 '청구항 3에 관하여' 같은 prose 언급 금지"** 규칙이 없다(grep 확인).
- 본문에서 "청구항 N" prose를 제거하는 **후처리 sanitizer도 없다**(grep 확인 — 3454는 `[청구항 구성]` 메타블록 제거, prose 아님).

### 1-2. ★ 생성이 주 출처 — 프롬프트가 "청구항"을 다수 참조
step_08 생성 프롬프트는 "청구항"을 근거로 삼으라고 반복 지시:
- 4385 "청구항에서 사용한 용어가 기준이다."
- 4412 "**청구항의 모든 구성요소**를 빠짐없이 포함하여 설명하라."
- 4489 "청구항에서 사용한 명칭과 상세설명의 명칭이 일치해야 한다."
→ LLM이 "청구항 3에 기재된 통신부(110)는…" / "청구항 3 및 청구항 5에 관련하여…"를 쓸 여지가 크고, **금지 규칙·후처리 제거가 없어 그대로 본문에 남는다.** 검토 반영은 이를 base로 보존하므로 사용자가 "반영 후" 본 것.

### 1-3. applyReview — 가드되나 **"제N항" 갭** + 유도 압력
- 가드(patent.js:**5268**): `if(/【청구항|청구항\s*\d+|.../.test(edit.content)) continue;` → "청구항 3" CONTENT 편집은 **드롭**(추가 안 함). 
- ⚠️ **갭**: 정규식에 **`제\s*\d+\s*항`(제3항) 형태가 없다** → "제3항 및 제5항에 관련하여" 편집은 통과·적용될 수 있다.
- edit-gen 입력 `[검토 결과] = filterReviewForScope(step_13)` 는 "청구항 N"으로 가득(검토가 청구항 뒷받침을 봄, 4674) → edit-gen이 "청구항 N"을 CONTENT에 echo하도록 **유도**(대부분 가드에 걸리나, 제N항·문장 일부는 누수 위험).

→ **정리:** ① 1차 출처 = 생성(금지 규칙 없음), 2차 = applyReview(가드되나 제N항 갭+유도). **공통 근인 = "본문 청구항-번호 언급 금지 규칙·후처리 부재."**

## 2. ★ 문제 ② — 예시도 설명이 외형만 (장치 구성에 의한 동작·구현 누락)

### 2-1. 예시도 설명 지시(4492)는 "예시도 자체(31~99)"만 요구
step_08의 예시도 설명 블록(patent.js:**4492**):
```
- 예시도(도 N)도 장치 도면과 동일한 수준으로 "도 N을 참조하면, …" 형태로
  ★그 구성·동작·부호★를 상세설명 본문에 반드시 기술하라. 아래 [예시도 설계]의 내용을 근거로 작성하라.
- 위 "번호(이름)"의 이름을 그대로 사용해 "이름(번호)" 형태로 기재하라.
```
- "그 구성·동작·부호" = **예시도 자신의 요소(31~99)** 를 말한다. 화면·시나리오의 **외형/요소** 중심.
- ⛔ **"예시도가 장치 도면 구성(통신부(110)·프로세서(120) 등 100~)에 의해 어떻게 동작·구현되는지"** 를 기술하라는 지시가 **없다.**
- ⛔ **예시도 요소(31~99) ↔ 장치 구성(100~) 연결**(소프트웨어 구성이 하드웨어로 구현) 지시가 **없다.**

### 2-2. [예시도 설계] 데이터(step_07c)도 외형만 — 장치 연결 정보 없음
- step_08에 주입되는 `[예시도 설계]`(4494) = `outputs.step_07c` = **refMap(31~99 이름) + briefDesc**.
- briefDesc = "도 N은 …예시도이다"(외형 한 줄). refMap = 예시도 요소 이름. → **장치 구성(100~)과의 연결·동작 정보가 데이터에 없다.**
- 예시도 생성 프롬프트(CONCEPT_PURPOSE_RULES 87-97)는 "그 요소가 청구항/상세설명의 **어느 구성에 대응하는지 알 수 있게** 하라"(91)고 **그리기(SVG) 시점**엔 연결 의도가 있으나, **설명(step_08) 데이터로 그 연결이 전달되지 않는다.**

### 2-3. 결과 — 외형 나열, 실질적 시나리오 안 됨
- LLM은 예시도 요소(검색창(31)…)와 외형만 기술 → "도 4를 참조하면, 검색창(31)이 화면 상단에 배치된다" 식 **외형 서술**.
- "이 검색창(31)은 **프로세서(120)가 실행하는 소프트웨어 모듈에 의해 렌더링되고, 통신부(110)를 통해 수신한 데이터를 표시한다**" 같은 **장치 구성에 의한 동작·구현(SW→HW, §42 실시가능성)** 이 **누락.**

## 5. 수정 방향

### A. 청구항 번호 본문 언급 금지 (문제 ①)
- **step_08 생성 + applyReview edit-gen 프롬프트**에 규칙 추가: "★ 상세설명 본문에 '청구항 N'·'제N항' 등 **청구항 번호를 직접 언급하지 마라.** 청구항에 기재된 구성은 **구성요소(참조번호) 형태(예: 통신부(110))로 구체 기술**하라."
- **applyReview 가드(5268)** 정규식에 `제\s*\d+\s*항` 추가 → "제N항" 편집도 드롭.
- (선택·안전망) 후처리 sanitizer: 본문의 "청구항\s*\d+ ?(및|또는|내지)? ?…에 (관하여|관련하여|있어서|기재된)" prose를 제거/완화(과도 제거 주의 — 최소 범위).

### B. 예시도 설명에 장치 구성에 의한 동작·구현 (문제 ②)
- **4492 예시도 설명 블록**에 지시 추가: "★ 예시도의 각 요소(31~99)가 **장치 도면 구성(100~) 중 어느 것에 의해 어떻게 동작·구현되는지** 기술하라(예: '검색창(31)은 프로세서(120)가 실행하는 소프트웨어에 의해 렌더링되고 통신부(110)가 수신한 데이터를 표시한다'). **소프트웨어 구성이 하드웨어(장치 구성)로 구체 동작·구현됨을 명확히**(§42 실시가능성). 예시도는 외형 나열이 아니라 **실질적·예시적 시나리오**로 기술하라."
- (선택) 예시도 생성 시 refMap에 **예시도 요소↔장치 구성 대응**을 캡처해 [예시도 설계] 데이터로 전달(LLM이 연결 근거 확보). 단 최소 변경은 4492 지시 강화(LLM이 이미 [장치 도면 설계]+[예시도 설계] 둘 다 보유하므로 연결 추론 가능).

## 7. 검증 관찰 포인트(수정 후)
- 생성·검토 반영 후 상세설명 본문에 "청구항 N/제N항" prose가 **나타나지 않나**(구성요소 형태로 기술).

- 예시도가 실질적·예시적 시나리오로 읽히나.
- 장치 설명·예시도 보존(#212·#213) 회귀 0.
