## 1. ★ 요구 1 — 식별번호 ↔ 도면번호 (현재 미적용 확정)

### 1-1. 현재: 식별번호는 31~99 전역 (도 번호 무관)
- 예시도 SVG 생성 프롬프트가 **"참조번호 31~99"** 로 지시(`patent.js:2972`)하고, REF_MAP 예시도 **`31: 요소이름 / 32: 요소이름`**(`2978~2979`)으로 고정 — **모든 도면이 31부터** 시작(도 5도 31~, 도 6도 31~ 또는 이어서). 도 번호 연동 없음.
- `_parseConceptRefMap`(`114·117`)은 SVG/REF_MAP에서 **n>=31 && n<=99** 만 수집 → LLM이 쓴 31~99를 그대로 `refMap[{signNumber,label}]`에 담음.
- step_08c 프롬프트 `_cList`(`4538`)는 `refMap`의 signNumber를 그대로 출력 → "도 5: … (참조번호: 검색창(31), 결과목록(32))" — **도 5인데 31,32**.
- → ★ 도 5 → 51~ / 도 6 → 61~ **미적용**. 본인 ① 확정.

### 1-2. 도 번호는 SoT(getAutoFigNums)이고 ③ override 로 동적
- `getAutoFigNums('step_07c')`(`3551`)=`computeFigNums(devCount,methCount,conceptN,cOverrides)`.`concept` — 장치 도면 수·**③ figNumOverride** 에 따라 도 번호가 **동적**(도 5가 ③로 도 3이 될 수 있음).
- 제목(【도 N】)은 **render 시점에 SoT로 동기화**: `_conceptSvgApplyTitle(svg, figNum)`(`220`)이 LLM의 【도 N】을 제거하고 getAutoFigNums 값으로 덮어씀(렌더 2323·다운로드). ③ 바뀌면 제목 자동 추종.
- ★ 그러나 **식별번호(31~99)에는 이런 SoT 동기화가 없다** — `_conceptSvgApplyRefNums` 같은 함수 부재. 그래서 번호는 LLM이 박은 31~99 그대로 고정.

### 1-3. 연동 방법 (수정 방향) — refMap = figNum 파생 SoT
식별번호를 도 번호 연동하려면 **도 N → N1,N2…(5x) 또는 N01,N02…(5xx)** 를 SoT로 두고, 네 소비처를 모두 정합시켜야 한다:
1. **SVG(svgContent)** — render 시 번호 치환(`_conceptSvgApplyRefNums(svg, figNum)`, 제목 패턴 이식): SVG의 (31)(32)를 (51)(52)로. ③ 바뀌면 자동 추종.
2. **refMap.signNumber** — figNum 파생값으로 (재)배정(canonical).
3. **step_08c 설명** — `_cList`가 refMap 읽으니 자동(생성 시 refMap이 5x면 설명도 5x).
4. **step_18 부호의 설명** — `_conceptRefPairs`(`149`)가 refMap 읽으니 자동.

**핵심 난점 — ③ override 정합:** 식별번호가 SVG에 박혀 있고(생성 시점) 도 번호는 ③로 사후 변동 → 생성 시 5x로 박으면 ③ 이동 시 불일치. 두 접근:
- **A(생성 시 지시 + override 재번호)**: SVG 생성 프롬프트(`2972·2978·2979`)에 "도 N의 요소는 N1,N2…로 번호" 지시(생성 시 figNums 이미 보유 `2961·2963`). ③ override 시 svgContent·refMap·step_08c **재번호** 필요.
- **B(render-SoT 재번호)**: 생성은 31~99 유지, **render/조립 시 figNum 파생으로 치환**(제목과 동일 패턴). refMap도 그 시점에 파생. step_08c·step_18은 refMap(파생) 읽음. ★ 단 step_08c는 **이미 생성된 텍스트**라 번호 치환을 텍스트에도 적용해야(생성 후 31→51 치환) — render-SoT의 텍스트 동기화가 까다로움.
- ★ **권장: A + 멱등 재번호 헬퍼**. 생성 시 figNum 기반 번호로 박고(도 5→51~), ③ override 시 `_conceptSvgApplyRefNums`(SVG)+refMap+step_08c를 figNum 파생으로 일괄 재번호(멱등). refMap을 원본 인덱스 기준으로 재계산하면 반복 적용에도 안전.

**번호 스킴 트레이드오프:**
- **5x(51~59)**: 도면당 9개 한계. 도 번호 2자리(도 10→10x)면 장치 100~과 충돌 위험.
- **5xx(510~599)**: 도면당 89개 여유, 장치(보통 100~199)와 충돌 적음(510+). 도 10→1010 등 길어짐.
- 예시도 도 번호는 보통 한 자리(5,6,7) → **5x 기본, 요소 多 또는 도번호 2자리는 5xx** 권장. 장치 부호(100~)와 구분 유지.

## 2. ★ 요구 2 — 예시도 내용 유기성

### 2-1. 현재 step_08c 프롬프트(`4544~4550`) — 일부 유기성 ★있음★
- ✅ **장치 구성 기초**: "예시도의 각 요소(31~99)가 [장치 도면 설계]의 어느 구성(100~, 프로세서(120)·통신부(110) 등)에 의해 어떻게 동작·구현되는지"(`4546`).
- ✅ **SW→HW 실시가능성(§42)**: "소프트웨어적 구성이 하드웨어(장치 구성)에 의해 구체적으로 동작·구현됨"(`4546`).
- ✅ **시나리오**: "외형 나열이 아니라 실질적·예시적 시나리오(동작 흐름)"(`4546`) + 예문(`4547`).
- (SVG 생성 측 `CONCEPT_PURPOSE_RULES`(`87~89`)도 "청구항 구성을 시각적으로 뒷받침·예시" 명시.)

### 2-2. 부족한 유기성 (본인 지적 — 보강 대상)
- ❌ **발명 일반/특수 예시 구분 없음**: "실질적·예시적 시나리오"는 있으나, **발명의 일반 실시예 + 특수(구체) 실시예**로 나눠 기술하라는 지시는 없음.
- ❌ **예시도 간 프로세스 연결·조립 유기성 약함**: "각 예시도를 '도 N을 참조하면…'으로 **개별** 기술"(`4545`) — 예시도/요소 간(도 5 → 도 6, 요소 31 → 32) **연결·조립이 끊김 없이 이어지는지** 명시 지시 없음. 각 도면이 고립 서술될 위험.
- ❌ **요소 간 데이터·제어 흐름**: 요소들이 장치 구성을 통해 **어떻게 맞물려 하나의 프로세스를 이루는지**(입력→처리→출력 연결)의 유기적 서술 지시 약함.

### 2-3. 보강 방향 (step_08c 프롬프트 강화 — LLM 호출 구조 무변경)
- 각 예시도를 **(가) 일반 실시예**(기본 동작) + **(나) 특수/구체 실시예**(특정 조건·예외)로 기술.
- **예시도 간·요소 간 연결**: "도 N의 요소(Nx)가 도 M의 요소(Mx)와 어떻게 이어지는지", 장치 구성(프로세서 등)을 매개로 **입력→처리→출력이 끊김 없이 조립**되는 프로세스로 서술.
- ★ 식별번호 연동(요구 1) 후엔 예문도 5x/6x 기반으로(도 5 요소 51 → 도 6 요소 61 흐름) — 두 요구가 맞물림.
