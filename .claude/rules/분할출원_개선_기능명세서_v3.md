# Phase 1: Gap 분석

기존 분할출원 모듈의 청구항 생성 로직을 11개 영역 기준으로 평가한다.

| # | 영역 | 현행 수준 | 심각도 | 구체적 누락 |
|---|------|-----------|--------|-------------|
| 1 | 사업 목적/맥락 | ⬤⬤⬤◯◯ | 🟠 | "바로 등록결정"이라는 분할출원의 실무 목적이 시스템에 명시되지 않음. 왜 A+B+C+D 형태로 출원하는지(등록 전례 활용 전략)가 프롬프트에 없음 |
| 2 | 기능 정의 | ⬤⬤⬤⬤◯ | 🟡 | 3유형(병합/카테고리/전략) 기능은 존재. 그러나 3유형 모두에 적용되는 **공통 절대 원칙**(신규사항 금지, basis 보존)이 유형별 프롬프트에 산발적으로만 반영됨 |

# Phase 3: 단계별 명세 작성

## 3-0. 분할출원 공통 절대 원칙

3가지 유형(병합·카테고리변경·전략) 모두 아래 원칙을 동일하게 적용한다. 유형별 차이는 "방향"뿐이며, 원칙은 하나다.

```javascript
// division.js 최상단에 정의
const DIVISION_PRINCIPLES = `
★★★ 분할출원 절대 원칙 (3유형 공통) ★★★

[원칙 1] 신규사항 추가 금지 (특허법 제52조 + 제47조)
- 분할출원 청구항의 모든 구성은 원출원의 최초 명세서(발명의 상세한 설명)에
  직접적으로 기재된 사항이어야 한다.
- 원출원 명세서에 없는 구성, 용어, 개념을 포함하면 신규사항 추가로 거절된다.
- AI는 "당업자의 자명한 도출"을 사용하지 말 것. 직접 기재 사항만 사용하라.

[원칙 2] 등록결정 구성(basis) 절대 보존
- 등록결정된 청구항의 구성(A+B+C)은 한 글자도 수정·삭제하지 않는다.
- 이 구성은 이미 심사관이 등록을 인정한 것이므로, 변경하면 등록 전례의
  이점을 잃고 새로운 거절이유가 발생할 수 있다.

[원칙 3] 추가 구성(D)의 출처 제한
- D는 반드시 원출원 "발명의 상세한 설명"에 기재되어 있으면서,
  원출원의 어떤 등록 청구항에도 포함되지 않았던 구성이어야 한다.
- D가 기존 종속항에 이미 있으면 이중 특허(double patenting) 위험이 있다.

[원칙 4] 바로 등록결정 전략
- A+B+C(등록 전례) + D(명세서 뒷받침, 추가 한정) = 거절이유 없음 → 바로 등록
- D 선택 시 "심사관이 거절하기 어려운" 구체적·구조적 한정을 우선 추천하라.
`;
```

### 3유형에서 이 원칙이 적용되는 방식

| 원칙 | 병합형 (merge) | 카테고리변경형 (category_change) | 전략형 (strategic) |
|------|----------------|--------------------------------|-------------------|
| 원칙1 신규사항 금지 | D는 명세서 직접 기재 구성만 | 변환 시 명세서에 없는 구성요소명(~부 등) 임의 생성 금지 | 새 독립항의 모든 구성에 명세서 단락번호 1:1 대응 필수 |
| 원칙2 basis 보존 | A+B+C 한 글자 수정 금지 | A+B+C의 기술적 내용 보존 (형태만 방법↔장치 전환) | basis를 참고하되, 새 독립항이므로 직접 보존 대신 "원출원 범위 내" 확인 |
| 원칙3 D 출처 제한 | 명세서에만 있고 기존 청구항에 없는 구성 | 변환 시 추가되는 구성도 명세서 기재 사항만 | 테마별 핵심 구성 모두 명세서 근거 필수 |
| 원칙4 바로 등록 전략 | basis + D → 등록 전례 활용 | 카테고리 변경 자체가 차별화 + D로 보강 | 새 관점이므로 전략 의도 다름, 그러나 명세서 범위 내 필수는 동일 |

## 3-1. 상태 전이 규칙

**변경 없음.** 기존 상태 전이 흐름을 그대로 유지한다.

```
upload → parsing → parsed → [결과확인]
→ analyzing → analyzed → [구성선택]
→ assembling → assembled → [비교검토]
→ verifying → verified → [명칭선택]
→ confirmed → generating → completed
```

유일한 내부 변경: `verifying` 상태에서 Pass 1(코드) → Pass 2(LLM) 순차 실행. 외부 상태 전이에는 영향 없음.

## 3-2. 유저 플로우 (개선된 부분 ★ 표시)

```
1. 사용자가 파일 업로드 (출원서 PDF, 등록결정서 PDF 등)
2. 시스템이 자동 분류 + 파싱
   ★ 파싱 시 명세서 전문을 spec_full_text에 1회 저장
3. 파싱 결과 확인 (등록 청구항, 명세서 단락)
4. 분할 유형 선택 (병합 / 카테고리변경 / 전략)
5. 분석 실행 — LLM이 추가 구성(D) 후보 추출
   ★ LLM 결과에 대해 코드 레벨 교차검증 자동 실행
   ★ 각 D에 명세서 근거 단락번호 + 원문 인용 표시
   ★ 기존 청구항과 70%+ 유사 시 overlap_warning 자동 부착
6. 사용자가 D 후보 선택
   ★ 선택 화면에 근거·위험도·overlap 경고 표시
7. 조립 실행 — basis(A+B+C) + 선택된 D → 분할 청구항 생성
   ★ 프롬프트에 DIVISION_PRINCIPLES 전문 주입
   ★ 조립 결과에 basis_preserved 확인 + added_components 추적
8. 비교 검토 (LCS diff로 원 청구항 vs 분할 청구항)
9. 검증 실행
   ★ Pass 1: 코드 레벨 자동 검증 (basis 보존, 이중특허, 키워드 존재)
   ★ Pass 2: LLM 의미 검증 (신규사항, 뒷받침, 형식)
   ★ 2-Pass 결과 통합 표시
10. 명칭 선택 → 확정 → Word 문서 생성
```

## 3-3. 예외/에러 처리

| # | 예외 상황 | 현행 대응 | 개선 대응 |
|---|-----------|-----------|-----------|

| E5 | 전략형에서 테마의 명세서 근거가 0건 | LLM이 임의 생성 가능 | 분석 결과에서 spec_paragraphs가 빈 테마는 risk_level=danger 자동 부여 |

## 3-4. 데이터 스키마

### 3-4-1. 테이블 변경 (기존 7개 테이블 중 2개만 수정)

```sql
-- [1] division_projects — 명세서 전문 저장 컬럼 추가
ALTER TABLE division_projects
ADD COLUMN IF NOT EXISTS spec_full_text TEXT;
-- 용도: 파싱 시 1회 저장. 이후 분석·조립·검증에서 재사용
-- 크기: 일반적 명세서 = 10,000~50,000자
-- 충돌: 기존 컬럼에 영향 없음. SELECT * 자동 포함

-- [2] division_validation_results — 코드 레벨 검증 결과 저장
ALTER TABLE division_validation_results
ADD COLUMN IF NOT EXISTS auto_verify_issues JSONB DEFAULT '[]'::jsonb;
-- 용도: Pass 1 (코드 자동 검증) 결과 저장
-- 구조: [{ severity, check, message, detail }]
-- 충돌: 기존 result_data(LLM 검증)와 분리 저장
```

### 3-4-2. JSONB 스키마 변경 (기존 필드 확장)

**division_unused_components.component_data (JSONB) — 필드 추가:**

```
기존 필드 (유지):
  paragraph_number, content, related_element, limitation_type,
  risk_level, risk_flags, insertion_point, suggestion

추가 필드:
  spec_source_text  STRING  -- 명세서 원문 인용 (뒷받침 근거 추적)
  overlap_warning   BOOLEAN -- 기존 청구항과 중복 경고
  overlap_detail    STRING  -- 중복 상세 ("기존 청구항 N에 유사 구성")
  registration_strategy STRING -- 바로 등록 전략 근거
```

**division_claims_output.draft_data (JSONB) — 필드 추가:**

```
기존 필드 (유지):
  division_claims[].claim_number, claim_type, parent_claim_number,
  claim_text, claim_text_highlighted

추가 필드:
  division_claims[].basis_preserved    BOOLEAN -- basis 원문 보존 확인
  division_claims[].added_components   ARRAY   -- 추가된 D 목록 [{content, paragraph_number, limitation_type}]
  new_matter_check                     STRING  -- 신규사항 확인 결과 요약
```

**충돌 검토:** JSONB이므로 필드 추가가 기존 데이터에 영향 없음. 기존 레코드에는 새 필드가 null/undefined로 존재하며, 코드에서 optional chaining(`?.`)으로 접근.

## 3-7. 프롬프트 상세 설계 (핵심 변경 사항)

### 3-7-1. 분석(Analyze) 프롬프트 — 3유형 공통 구조

모든 유형의 분석 프롬프트는 아래 구조를 따른다:

```
[1] DIVISION_PRINCIPLES (공통 원칙 4개 — 상수에서 주입)
[2] 유형별 분석 지시 (병합/카테고리변경/전략에 따라 다름)
[3] 입력 데이터 (basis 청구항, 전체 청구항, 명세서 전문)
[4] 출력 JSON 스키마
```

**병합형 — 유형별 분석 지시:**
```
이것은 "병합형" 분할출원이다. 
목적: 등록 청구항(A+B+C)을 그대로 유지하면서, 명세서에만 있고 기존 어떤 
청구항에도 없었던 구성(D)을 추가하여 A+B+C+D로 출원한다.
방향: 구체화·한정·부가만 허용. 카테고리 변경 제안 절대 금지.
```

**카테고리변경형 — 유형별 분석 지시:**
```
이것은 "카테고리 변경형" 분할출원이다.
목적: 등록 청구항의 기술적 내용(A+B+C)을 보존하면서, 방법↔장치 카테고리를 
전환하고, 명세서 기재 사항 내에서 변환에 필요한 구성을 추출한다.
방향: 변환 시 명세서에 없는 구성요소명(~부, ~수단 등)을 임의 생성하지 마라.
      명세서에 명시적으로 기재된 구성요소명만 사용하라.
```

**전략형 — 유형별 분석 지시:**
```
이것은 "전략형" 분할출원이다.
목적: 등록 청구항과 다른 관점의 새로운 독립항을 명세서 범위 내에서 작성한다.
방향: 신규사항 추가 위험이 가장 높은 유형이다.
      각 테마의 핵심 구성은 반드시 명세서 단락번호와 1:1 대응이 있어야 한다.
      명세서에 단 한 문장도 근거가 없는 테마는 제안하지 마라.
      출력의 모든 구성에 spec_source_text(명세서 원문 인용)를 반드시 포함하라.
```

## 3-8. 코드 레벨 검증 함수 상세

```javascript
/**
 * Pass 1: 코드 레벨 자동 검증 (LLM 호출 전)
 * 3유형 공통으로 사용. divisionType에 따라 일부 검증 항목 분기.
 */
function runAutoVerify(divisionClaims, basisClaim, allOriginalClaims, specFullText, divisionType) {
  var issues = [];
  var basisText = basisClaim ? (basisClaim.amended_text || basisClaim.original_text || '') : '';

  // ─── [검증 1] basis 보존 확인 (병합형·카테고리변경형) ───
  if (divisionType === 'merge') {
    divisionClaims.filter(function(c){ return c.claim_type === 'independent'; }).forEach(function(c) {
      // basis 원문의 앞 100자가 분할 독립항에 포함되어 있는지
      if (basisText && !c.claim_text.includes(basisText.substring(0, 100))) {
        issues.push({
          severity: 'CRITICAL', check: 'basis_preservation',
          message: '독립항에서 등록결정 구성(basis)이 변경된 것으로 보입니다',
          detail: 'basis 앞 100자: "' + basisText.substring(0, 50) + '..."'
        });
      }
    });
  }

  // ─── [검증 2] 이중 특허 방지 (3유형 공통) ───
  divisionClaims.forEach(function(dc) {
    allOriginalClaims.forEach(function(oc) {
      var ocText = oc.amended_text || oc.original_text || '';
      var sim = _lcsRatio(dc.claim_text, ocText);
      if (sim > 0.95) {
        issues.push({
          severity: 'HIGH', check: 'double_patenting',
          message: '분할 청구항 ' + dc.claim_number + '이 원출원 청구항 ' + oc.claim_number + '과 ' + Math.round(sim*100) + '% 동일',
          detail: '이중 특허 위험 — 추가 구성(D)이 충분히 차별화되지 않았습니다'
        });
      }
    });
  });

  // ─── [검증 3] 신규사항 위험 — 키워드 기반 (3유형 공통) ───
  if (specFullText) {
    divisionClaims.forEach(function(dc) {
      var keywords = (dc.claim_text.match(/[가-힣]{2,}/g) || []);
      // 불용어 제외
      var stopwords = ['상기','있어서','포함하는','특징으로','하는','에서','으로','위한','의한','대한'];
      var meaningful = keywords.filter(function(kw){ return stopwords.indexOf(kw) < 0 && kw.length >= 3; });
      var missing = meaningful.filter(function(kw){ return specFullText.indexOf(kw) < 0; });
      if (missing.length > 3) {
        issues.push({
          severity: 'HIGH', check: 'new_matter_risk',
          message: '청구항 ' + dc.claim_number + '에 명세서 미발견 용어 ' + missing.length + '개',
          detail: '미발견: ' + missing.slice(0, 5).join(', ') + (missing.length > 5 ? ' 외 ' + (missing.length-5) + '개' : '')
        });
      }
    });
  }

  // ─── [검증 4] 추가 구성(D) 교차 확인 (added_components 있을 때) ───
  divisionClaims.forEach(function(dc) {
    if (dc.added_components && dc.added_components.length) {
      dc.added_components.forEach(function(comp) {
        // 기존 모든 청구항과 LCS 유사도
        allOriginalClaims.forEach(function(oc) {
          var ocText = oc.amended_text || oc.original_text || '';
          var sim = _lcsRatio(comp.content || '', ocText);
          if (sim > 0.7) {
            issues.push({
              severity: 'MEDIUM', check: 'component_overlap',
              message: '추가 구성 "' + (comp.content||'').slice(0,20) + '..."이 기존 청구항 ' + oc.claim_number + '과 ' + Math.round(sim*100) + '% 유사',
              detail: '이중 특허 위험 검토 필요'
            });
          }
        });
      });
    }
  });

  return issues;
}

/**
 * LCS 유사도 비율 (0~1). 기존 _lcsTokens 함수 활용.
 */
function _lcsRatio(a, b) {
  if (!a || !b) return 0;
  var tokA = a.replace(/[^가-힣a-zA-Z0-9]/g,' ').split(/\s+/).filter(Boolean);
  var tokB = b.replace(/[^가-힣a-zA-Z0-9]/g,' ').split(/\s+/).filter(Boolean);
  if (!tokA.length || !tokB.length) return 0;
  var lcsLen = _lcsTokens(tokA, tokB).length;
  return lcsLen / Math.max(tokA.length, tokB.length);
}
```

# 외부 전문가 5인 검증

## 👤 전문가 1 — 특허 실무 변리사 (분할출원 전문, 20년)

**검토 범위:** 원칙 1~4의 실무 정확성, 3유형별 원칙 적용 타당성

> **1. 원칙 설계에 대해:** 4대 원칙이 실무를 정확히 반영한다. 특히 "AI는 당업자의 자명한 도출을 사용하지 말 것"이라는 지시가 핵심이다. 실무에서는 자명한 도출을 주장할 수 있지만, AI가 이를 잘못 판단하면 신규사항 추가로 직결되므로 보수적 접근이 맞다.
>
> **2. 3유형 공통 적용에 대해:** 올바르다. 실무적으로 병합형이든 전략형이든 "원출원 명세서 범위 내"라는 대원칙은 동일하다. 다만 전략형의 원칙2(basis 보존)를 "직접 보존 대신 원출원 범위 내 확인"으로 완화한 것은 적절하다. 전략형은 새 독립항이므로 basis를 그대로 복사하는 것이 아니라, 명세서 범위 내에서 새로 작성하는 것이기 때문이다.
>
> **3. 보완 권고:** 카테고리변경형에서 "방법→장치 변환 시 명세서에 ~부가 없으면 임의 생성 금지"는 맞지만, **변환 매핑 테이블**(단계→구성요소 대응)을 명세서 원문 기반으로 먼저 만들고 이를 프롬프트에 입력하면 더 안전하다. 향후 확장으로 기록한다.

**결론:** ✅ 승인

## 👤 전문가 2 — 특허청(KIPO) 심사관 출신 (15년)

**검토 범위:** 심사 기준 부합성, 검증 항목 완전성

> **1. 검증 항목에 대해:** 5개 검증 항목(신규사항, basis 보존, 이중특허, 뒷받침, 형식)이 심사관이 실제로 보는 항목과 일치한다. 우선순위 배치도 적절하다. 신규사항이 CRITICAL인 것이 맞다.
>
> **2. 2-Pass 구조에 대해:** 코드 레벨 검증(Pass 1)이 LLM 검증 전에 실행되는 것은 좋다. 특히 basis 보존 검사와 이중특허 유사도 검사는 문자열 비교로 충분하므로 LLM에 맡길 필요가 없다. 다만 **키워드 기반 신규사항 검사(Pass 1의 검증 3)는 불용어 목록을 더 확충해야 한다.** "포함하는", "구성되는", "수행하는" 같은 특허 문체 상용어가 빠지면 오탐이 많아진다.
>
> **3. 보완 권고:** 불용어 목록에 특허 문체 상용어 20~30개 추가. 예: '구성되는', '수행하는', '이루어지는', '형성되는', '제공하는', '생성하는', '출력하는', '수신하는', '전송하는', '저장하는' 등.

**결론:** ✅ 승인 (불용어 확충 조건부)

## 👤 전문가 3 — 프론트엔드/UX 아키텍트

**검토 범위:** UI 변경의 기존 시스템 영향, 사용자 경험

> **1. UI 변경에 대해:** 구성 카드에 📄 근거, 📝 인용문, 🔴 overlap 경고를 추가하는 것은 기존 `.division-component-card` 내부에 DOM 요소를 추가하는 것이므로 다른 탭에 영향 없다. CSS는 `division-` 접두사를 사용하므로 충돌 없다.
>
> **2. 검증 결과 2-Pass 표시에 대해:** Pass 1과 Pass 2를 별도 섹션으로 나누는 것은 좋다. 사용자가 "코드가 자동으로 잡은 것"과 "AI가 의미적으로 판단한 것"을 구분할 수 있다. 다만 **severity별 색상 코딩을 통일해야 한다:** CRITICAL=빨강, HIGH=주황, MEDIUM=노랑. 기존 opinion.js의 검증 결과 화면과 색상 체계를 맞추면 사용자 학습 비용이 줄어든다.
>
> **3. 보완 권고:** severity 색상을 opinion.js와 통일. 기존 CSS 변수(`--color-error`, `--color-warning`)를 재사용.

**결론:** ✅ 승인

## 👤 전문가 4 — 백엔드/DB 아키텍트

**검토 범위:** 스키마 변경 안전성, 데이터 정합성, 성능

> **1. spec_full_text 컬럼에 대해:** TEXT 타입으로 50,000자까지 저장하면 단일 레코드당 ~100KB. Supabase의 행 크기 제한(기본 8KB → toast 테이블로 자동 분리)에 걸리지만, PostgreSQL이 자동으로 TOAST 처리하므로 문제없다. 다만 **이 컬럼을 SELECT *로 항상 로드하면 불필요한 데이터 전송이 발생한다.** 프로젝트 목록 조회에서는 spec_full_text를 제외하고, 분석/조립/검증 시에만 명시적으로 조회해야 한다.
>
> **2. JSONB 필드 추가에 대해:** 기존 레코드에 새 필드가 없어도 JSONB는 null로 처리하므로 안전하다. optional chaining(`?.`)으로 접근하라는 명세가 적절하다.
>
> **3. auto_verify_issues 컬럼에 대해:** JSONB 배열로 저장하는 것은 적절하다. Pass 1 결과는 구조가 단순하고 검색할 필요가 없으므로 JSONB가 맞다.
>
> **4. 보완 권고:** 프로젝트 목록 조회 쿼리에서 `select('*, !spec_full_text')` 또는 필요한 컬럼만 명시적으로 선택하도록 코드 수정 필요. 대형 텍스트 컬럼의 불필요한 로드 방지.

**결론:** ✅ 승인 (SELECT 최적화 조건부)

## 👤 전문가 5 — LLM 프롬프트 엔지니어 (특허 AI 시스템 전문)

**검토 범위:** 프롬프트 설계 품질, LLM 할루시네이션 방어, 출력 안정성

> **1. DIVISION_PRINCIPLES 상수화에 대해:** 9곳의 프롬프트에 동일 원칙을 주입하는 구조가 올바르다. 원칙이 프롬프트 상단에 위치하면 LLM이 더 강하게 준수한다. 다만 **원칙 텍스트가 400토큰 이상이므로, 분석·조립·검증 각각에서 원칙 전문 + 명세서 전문(수만 자)을 합치면 컨텍스트 윈도우 부담이 크다.** 명세서 전문은 관련 단락만 발췌하여 전달하는 옵션도 고려해야 한다.
>
> **2. 3유형 공통 구조에 대해:** `[원칙] + [유형별 지시] + [입력] + [출력 스키마]` 4단 구조가 명확하다. 유형별 지시가 짧고 구체적이어서 LLM이 혼동할 여지가 적다.
>
> **3. JSON 출력 안정성에 대해:** spec_source_text(명세서 원문 인용) 필드를 추가하면 LLM 출력 길이가 증가한다. **JSON 파싱 실패 시의 폴백이 기존에 있는지 확인 필요.** 기존 `App.callClaude` 후 JSON.parse 실패 시 재시도 로직이 있다면 충분하다.
>
> **4. 할루시네이션 방어에 대해:** 코드 레벨 교차검증(Pass 1)이 LLM 할루시네이션의 최종 방어선으로 적절하다. 특히 키워드 기반 신규사항 검사는 LLM이 명세서에 없는 용어를 사용했을 때 즉시 감지할 수 있다.
>
> **5. 보완 권고:** 명세서 전문이 40,000자를 초과하면 LLM 입력 시 `substring(0, 40000)` 트리밍이 필요하다. 기존 분석 프롬프트에서 이미 `specText.substring(0, 40000)` 처리가 있으므로 이를 유지하되, 검증 프롬프트에서도 동일하게 적용해야 한다.

**결론:** ✅ 승인 (컨텍스트 크기 관리 조건부)
