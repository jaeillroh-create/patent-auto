# 분할출원 검증-수정 루프 기능명세서

> **작성일:** 2026-04-07  
> **전제:** 분할출원_개선_기능명세서_v3.md 의 T12~T14 검증 파이프라인이 구현된 상태  
> **대상:** division.js 내 검증(verify) → 수정(correct) → 재검증 루프

---

## 1. 사업 목적

검증에서 발견된 문제를 사용자가 확인하고 수정한 후 재검증하여, **신규사항 추가 없는 적법한 분할출원 청구항**을 확정하는 것이 목적이다.

현재는 검증 결과를 보여주기만 하고, 문제가 있어도 수정 경로가 없다.

---

## 2. 핵심 설계 원칙

### 2.1 뒷받침 검증의 실무 기준

특허법상 "명세서에 의해 뒷받침된다"의 판단 기준:

- **직접 기재:** 명세서에 동일한 표현이 있음 → pass
- **실질적 뒷받침:** 표현은 다르지만, 명세서의 기술적 내용이 해당 구성을 실질적으로 설명하고 있음 → pass (근거 단락 명시 필요)
- **자명한 도출:** 당업자가 명세서 내용으로부터 자명하게 도출할 수 있음 → warning (위험하지만 주장 가능)
- **근거 없음:** 명세서 어디에도 해당 구성의 근거가 없음 → fail (신규사항)

**AI 검증 시 주의사항:**
- 단순 키워드 매칭으로 "용어가 다르다"고 바로 fail 처리하면 안 됨
- 명세서에서 동일한 기술적 개념을 다른 표현으로 설명하고 있는 경우를 인식해야 함
- 예: 청구항 "데이터 정합성 검증부" vs 명세서 "수신된 데이터의 무결성을 확인하는 모듈" → 실질적 뒷받침 인정

### 2.2 검증 결과 분류 체계

| 등급 | 의미 | 사용자 액션 |
|------|------|------------|
| ✅ pass | 명세서에 의해 뒷받침됨 (직접 기재 또는 실질적 뒷받침) | 없음 |
| ⚠️ warning | 뒷받침 가능하나 위험 요소 있음 (자명한 도출, 간접적 근거) | 검토 후 수용/수정 선택 |
| ❌ fail | 명세서에 근거 없음 (신규사항 위험) | 반드시 수정 필요 |

## 3. 유저 플로우

```
[검증 결과 확인]
    │
    ├── 전부 pass → "최종 확정" 버튼 활성화
    │
    ├── warning 있음 → 사용자 검토
    │     ├── "수용" → 해당 항목 pass로 전환, 사유 기록
    │     └── "수정 필요" → 수정 모드 진입
    │
    └── fail 있음 → 수정 필수
          │
          [수정 모드]
          │
          ├── 선택지 1: 해당 구성(D) 제거 → 다른 D 선택 → 재조립 → 재검증
          │
          ├── 선택지 2: 청구항 문언 직접 수정 → 재검증
          │
          └── 선택지 3: 뒷받침 근거 보강 (명세서 단락 추가 지정) → 재검증
          
[재검증 결과 확인] → 전부 pass면 "최종 확정"
```

## 4. 검증 결과 화면 개선

### 4.1 각 검증 항목에 액션 버튼 추가

```
┌─────────────────────────────────────────────────────────┐
│ ⚠️ warning — 명세서 뒷받침 (간접적)                        │
│                                                           │
│ 청구항: "데이터 정합성 검증부"                               │
│ 명세서: 【0098】"수신된 데이터의 무결성을 확인하는 모듈이..."   │
│ 판단: 표현은 다르나 동일 기술적 개념. 실질적 뒷받침 가능.       │
│                                                           │
│   [✅ 수용 (실질적 뒷받침 인정)]  [✏️ 수정]                  │
└─────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────┐
│ ❌ fail — 신규사항 위험                                    │
│                                                           │
│ 청구항: "블록체인 기반 인증 모듈"                            │
│ 명세서: 해당 구성의 근거 단락 없음                           │
│ 판단: 명세서에 "블록체인" 관련 기재 없음. 신규사항 추가에 해당  │
│                                                           │
│   [🗑️ 해당 구성 제거]  [✏️ 문언 수정]  [📄 근거 단락 지정]  │
└─────────────────────────────────────────────────────────┘
```

### 4.2 수정 모드 UI

**선택지 1: 해당 구성 제거 → 분석 화면으로 돌아가 다른 D 선택**
```
버튼: "🗑️ 해당 구성 제거"
→ 확인 모달: "이 구성을 제거하고 다른 구성을 선택하시겠습니까?"
→ 분석 화면으로 이동 (기존 선택에서 해당 구성 체크 해제)
→ 재조립 → 재검증
```

**선택지 2: 청구항 문언 직접 수정**
```
버튼: "✏️ 문언 수정"
→ 해당 청구항 텍스트를 편집 가능한 textarea로 전환
→ 수정 후 "재검증" 버튼
→ 수정된 텍스트로 검증 Pass 2(LLM) 재실행
  ★ 재검증 프롬프트에 "수정 전 문언"과 "수정 후 문언"을 모두 제공
  ★ 수정 후 문언이 여전히 명세서에 뒷받침되는지 집중 검증
```

**선택지 3: 뒷받침 근거 보강**
```
버튼: "📄 근거 단락 지정"
→ 명세서 단락 목록 표시 (검색 가능)
→ 사용자가 "이 단락이 근거다"라고 지정
→ 재검증 시 해당 단락을 집중 검토
  ★ "사용자가 【0123】을 근거로 지정했다. 이 단락이 해당 구성을 
     실질적으로 뒷받침하는지 판단하라"
```

## 5. 검증 프롬프트 강화 — 실질적 뒷받침 판단

### 5.1 기존 검증 프롬프트에 추가할 지시

```
[뒷받침 판단 기준 — 실무 수준]

"뒷받침된다"는 것은 동일한 단어가 명세서에 있다는 것이 아니다.
명세서의 기술적 내용이 해당 청구항 구성을 실질적으로 설명하고 있으면 
뒷받침이 인정된다.

판단 절차:
1. 청구항의 각 구성요소를 분리한다
2. 각 구성요소에 대해 명세서에서 대응하는 기술적 설명을 찾는다
3. 대응 관계를 판단한다:
   - "직접 기재": 명세서에 동일/거의 동일한 표현 있음 → pass
   - "실질적 뒷받침": 표현은 다르지만 동일 기술적 개념 → pass 
     (근거 단락번호 + 대응 설명 기재)
   - "자명한 도출": 명세서 내용에서 당업자가 도출 가능 → warning
     (근거 단락번호 + 도출 논리 기재)
   - "근거 없음": 명세서에 대응하는 기술적 내용 없음 → fail

예시:
- 청구항 "정합성 검증부" vs 명세서 "무결성 확인 모듈" 
  → pass (실질적 뒷받침, 동일 기술적 개념)
- 청구항 "딥러닝 기반 분석부" vs 명세서 "기계학습 모델을 활용한 분석"
  → warning (딥러닝⊂기계학습이지만 명세서가 딥러닝을 특정하지 않음)
- 청구항 "블록체인 인증 모듈" vs 명세서에 블록체인 언급 없음
  → fail (신규사항)

출력의 각 항목에 아래 필드를 포함하라:
- check_type: "spec_support" | "new_matter" | "basis_scope" | "format" 등
- result: "pass" | "warning" | "fail"
- claim_element: 검증 대상 청구항 구성요소
- spec_paragraph: 근거 단락번호 (있을 경우)
- spec_quote: 명세서 근거 원문 (30자 이내 발췌)
- support_type: "direct" | "substantial" | "derivable" | "none"
- reasoning: 판단 근거 설명
```

### 5.2 재검증 프롬프트 (수정 후)

```
"아래 분할출원 청구항이 수정되었다. 수정 전후를 비교하고,
수정 후 청구항이 원출원 명세서에 의해 뒷받침되는지 재검증하라.

[수정 전 청구항]
{beforeText}

[수정 후 청구항]  
{afterText}

[수정 사유]
{reason}

{사용자가 근거 단락을 지정한 경우:}
[사용자 지정 근거 단락]
{userSpecifiedParagraphs}
→ 이 단락이 수정된 구성을 실질적으로 뒷받침하는지 집중 검토하라.

[원출원 명세서 전문]
{specFullText}

★★★ 분할출원 절대 원칙 적용 ★★★
{DIVISION_PRINCIPLES}

검증 항목은 기존과 동일 (신규사항 → basis 보존 → 이중특허 → 뒷받침 → 형식)"
```

## 6. 상태 전이 변경

```
기존:
  ... → verifying → verified → [명칭선택] → confirmed

변경:
  ... → verifying → verified → [검증결과 검토]
                                    │
                                    ├── 전부 pass → [명칭선택] → confirmed
                                    │
                                    └── warning/fail 있음 → [수정]
                                          │
                                          ├── 구성 제거 → analyzed (분석 화면)
                                          ├── 문언 수정 → re_verifying → verified
                                          └── 근거 보강 → re_verifying → verified
```

**새 상태:** `re_verifying` (재검증 중)  
기존 `verifying`과 동일한 로직이지만, 수정 이력을 추적하기 위해 별도 상태.
